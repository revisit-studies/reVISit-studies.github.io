Version 3.0 of reVISit is out! Where 2.4 was all about stability, 3.0 is a big feature release. Highlights include **declarative experiment design with factors**, **global variables** that carry state across trials, **templating** for reusing components, **webcam recording**, **recruitment controls for between-subjects designs**, and **dark mode**. For the complete list of changes, take a look at the [release notes on GitHub](https://github.com/revisit-studies/study/releases/tag/v3.0.0).

### Should I Update Now?

We recommend 3.0 for all new studies. If you have a study on 2.4 that you've already tested and piloted and plan to launch soon, stay on 2.4 until data collection is done. After updating, run pilots on 3.0 to check that everything works as expected.

3.0 is a major version, so there are a few things to check when you upgrade:

- **Firebase users** need to create two new Firestore composite indexes before the first participant starts. ReVISit blocks study startup if they are missing. See [Create indexes for participant sequence assignment](https://revisit.dev/docs/data-and-deployment/firebase/setup/#create-indexes-for-participant-sequence-assignment).
- **Self-hosted Supabase users** should read the [Supabase setup guide](https://revisit.dev/docs/data-and-deployment/supabase/setup/) before upgrading. reVISit now uses a pinned upstream Supabase deployment, and existing MinIO or pgsty stacks need to follow the migration guide.
- **React stimulus authors**: reVISit now runs on React 19 and Mantine 9. If your study includes custom React components, pilot them carefully.

Now let's look at what's new in 3.0!

## Designing Experiments

### Declarative Study Design with Factors

Most experiments mix within- and between-subjects variables. Building those designs component by component gets tedious, especially for something like a Stroop test with dozens of color/congruence combinations. With 3.0, you can declare your experiment's **factors** and let reVISit generate the trials.

Factors are declared at the top level of the Study Config and combined with **actions** like `cross`, `zip`, `concat`, `repeat`, `keep`/`remove`, and `sample`:

```json
"factors": {
  "color": ["RED", "ORANGE", "YELLOW", "GREEN", "BLUE"],
  "congruence": ["neutral", "incongruent"],
  "stroopConditions": {
    "action": "cross",
    "factors": ["color", "congruence"]
  },
  "fontSize": ["24px", "48px"]
},
"betweenSubjects": ["fontSize"]
```

A `factor` block in the sequence then creates one trial per condition, and each trial receives its condition as `parameters`:

```json
{
  "type": "factor",
  "id": "stroopTrials",
  "factor": "stroopConditions",
  "components": "stroopTrial",
  "order": "random"
}
```

Factors listed in `betweenSubjects` are assigned once per participant and passed to every component. Actions can be nested, so complex designs like a mixed between/within correlation perception study fit into a few lines of JSON. Try the [Stroop factors demo](https://revisit.dev/study/demo-stroop-factors/) and the [HTML version](https://revisit.dev/study/demo-stroop-html-factors/), and read the [factors documentation](https://revisit.dev/docs/designing-studies/factors/) for the full set of actions.

### Templating with Variables

Many text fields in a Study Config now accept `{{variable}}` placeholders, filled in from a component's `parameters`. This lets you define a component once and reuse it across many trials, changing only what differs:

```json
"baseComponents": {
  "quizQuestion": {
    "type": "markdown",
    "instruction": "Which city is the capital of {{country}}?",
    "path": "myStudy/assets/{{hintFile}}.md"
  }
},
"components": {
  "quiz-1": {
    "baseComponent": "quizQuestion",
    "parameters": { "country": "France", "hintFile": "hint-europe" }
  }
}
```

Templates work in instructions, response prompts, option labels, markdown files, help text, and component paths. HTML stimuli can opt in with `"templated": true`. Helpers such as `lookupAnswersRel` and `ifEquals` let you refer to a participant's earlier answers or show different text depending on a value, for example "Last time, you said {{lookupAnswersRel -1 "capital-answer"}}." Templating is also how factor conditions reach your components. See the [templating documentation](https://revisit.dev/docs/designing-studies/templating/) and the [templating demo](https://revisit.dev/study/demo-templating).

### Global Variables

Some studies need state that persists across trials, such as a remaining budget, a running score, or an eligibility flag. **Global variables** handle this. Declare them in the Study Config, show them in any templated field, and update them when a participant submits a response:

```json
"globalVariables": {
  "budget": { "initialValue": 100, "min": 0 }
}
```

```json
{
  "id": "cost",
  "type": "numerical",
  "prompt": "You have {{globalVariables.budget}} left. How much will you spend?",
  "max": "{{globalVariables.budget}}",
  "onSubmit": [{ "variable": "budget", "operation": "subtract" }]
}
```

Updates are applied only on submit. Editing a field or clicking **Previous** does not change the value, and validation rules like `min` reject submissions that would push a variable out of range. Global variable values are included in the tidy CSV export, and replay lets analysts step through each participant's submission history. See the [global variables documentation](https://revisit.dev/docs/designing-studies/global-variables/).

## Recording and Input

### Webcam Recording

In 2.3 we introduced screen recording. 3.0 adds **webcam recording**, which works on its own or alongside screen and audio recording. Enable it with `recordWebcam` in `uiConfig` or on individual components:

```json
"uiConfig": {
  "recordScreen": true,
  "recordWebcam": true
}
```

Webcam-only studies can use the new [`webcam-recording` library](https://revisit.dev/docs/libraries/webcam-recording/) for the permission page. In participant replay, screen and webcam recordings play in sync, and you can view them side by side, picture-in-picture, or with the webcam on top.

![Participant replay with synchronized webcam and screen recordings, using the "Webcam on top" layout](/img/blog_posts/2026-11-09-release-3.0/screen-webcam-layout.png)

If an analyst replays a recording in a different browser from the one the participant used, reVISit now shows a warning, since video playback can depend on the browser. See [Record Screen and Webcam](https://revisit.dev/docs/designing-studies/record-screen/) to get started.

### Keyboard Shortcuts and Gamepad Input

`buttons` responses now support keyboard shortcuts. Give an option a `key` and participants can answer without the mouse, which is useful for timed tasks:

```json
"options": [
  { "label": "Red", "value": "red", "key": "r" },
  { "label": "Blue", "value": "blue", "key": "b" }
]
```

reVISit can also record **gamepad** button and axis events with `captureGamepad`. The events are stored with each component's window events. See [Keyboard and Gamepad Input](https://revisit.dev/docs/designing-studies/input-devices/).

### Drawing Library

The new [`drawing` library](https://revisit.dev/docs/libraries/drawing/) adds a freehand drawing canvas built on Excalidraw, with pen, eraser, colors, pen sizes, and undo/redo. The final drawing is saved as the response, and the drawing process is captured with provenance tracking so you can replay it. Try the [drawing demo](https://revisit.dev/study/library-drawing).

## Forms

Forms got a lot of attention in this release:

- **Validation**: `shortText` and `longText` responses support character and word limits, `textValidation` rules (including regular expressions), and built-in formats such as email, URL, and phone number. Numerical and other responses gained min/max and range validation. See [Text Length and Content Validation](https://revisit.dev/docs/designing-studies/forms/#text-length-and-content-validation).
- **Conditional follow-up questions**: Use `visibleIf` to show a response only when another response in the same component meets a condition, such as asking for a university name only if the participant attended one. See [Conditional Follow-up Questions](https://revisit.dev/docs/designing-studies/forms/#conditional-follow-up-questions).
- **Clearing selections**: Participants can deselect radio buttons. See [Clearing Selections](https://revisit.dev/docs/designing-studies/forms/#clearing-selections).
- **Requiring values from stimuli**: Reactive responses can require a specific value from a stimulus before the participant can continue. See [Requiring a Value from a Stimulus](https://revisit.dev/docs/designing-studies/forms/#requiring-a-value-from-a-stimulus).
- **Delayed responses**, improved feedback options, and NASA-TLX and SMEQ sliders that preview their value on hover.

## Styling and Appearance

### Dark Mode

Set `uiConfig.colorMode` to `light`, `dark`, or `userPreference` to choose the study's appearance. The chosen mode is saved with the participant's data, so resumed sessions and replays look the same as the original. Embedded website components inherit the mode by default and can override it. Built-in controls support both modes, but your own stimuli may need adjusting, so check them in every mode your study allows. Try the [dark mode demo](https://revisit.dev/study/demo-dark-mode) and read the [Color Mode documentation](https://revisit.dev/docs/designing-studies/applying-style/#color-mode).

### Form Style and Layout

A reusable **Google Forms style** gives questionnaires a card-based look without writing CSS. We also refined default response widths, so compact fields like numbers and dates no longer stretch across the whole page, and you can now style the required-field asterisk with CSS. See [Applying Styles](https://revisit.dev/docs/designing-studies/applying-style/).

## Running Studies

### Recruitment Controls for Between-Subjects Designs

[Stage Management](https://revisit.dev/docs/analysis/stage-management/) can now manage recruitment for between-subjects factors. For the active stage, you can:

- Monitor current, completed, and total participants for each combination of factor levels.
- Enable or disable recruitment to individual conditions.
- Set a maximum number of participants, divided evenly across conditions or set manually for each one.
- **Time out** abandoned participants to free their place for a replacement.

When a stage is full, new participants see a clear **Study full** page instead of being admitted. Together with [URL conditions](https://revisit.dev/docs/designing-studies/sequences/url-conditions/) from 2.4, this makes it much easier to hit your target sample size in each condition.

### Landing Page Tabs and Study Visibility

You can now group the studies on your landing page into tabs with Markdown descriptions by editing `public/global.json`. You can also hide individual studies from the landing page in the analysis interface's **Manage** tab, for example so participants can't browse to other conditions. Hiding a study only removes it from the list; its direct link still works. See [Configuring the Landing Page](https://revisit.dev/docs/data-and-deployment/landing-page/).

![The landing page with Demo Studies, Tutorials, and Studies tabs](/img/blog_posts/2026-11-09-release-3.0/configured-tabs.jpg)

### Datastore Controls

A new **Datastore** tab shows which storage backend a study is configured with and which one analytics is reading from, and links straight to your Firebase or Supabase console. Administrators can also temporarily switch new sessions to local storage. See [Choose Storage for New Sessions](https://revisit.dev/docs/analysis/data-management/#choose-storage-for-new-sessions).

### Export a Page as PDF

You can now save the current study page as a PDF from the **Study actions** menu, which is handy for sharing study materials with collaborators or including them in a paper's supplementary material. See [Preview and Export a Study Page](https://revisit.dev/docs/designing-studies/previewing-studies/).

## Deployment, Security, and Performance

- **Firebase App Check with reCAPTCHA Enterprise**: New Firebase deployments can use Fraud Defense (reCAPTCHA Enterprise). Existing reCAPTCHA v3 setups keep working, and there's a [step-by-step migration guide](https://revisit.dev/docs/data-and-deployment/firebase/setup/#migrate-an-existing-v3-deployment).
- **Supabase**: Self-hosted Supabase now uses a pinned upstream deployment with a documented migration and rollback path. See the [Supabase setup guide](https://revisit.dev/docs/data-and-deployment/supabase/setup/).
- **Faster startup**: The study interface now renders while participant assignment is still resolving, and assignment itself is faster.
- **Safari fix**: We fixed 30–50 second stalls in Safari when connecting to Firestore.
- **Data safety**: Replays can no longer overwrite participant metadata, completed submissions are better protected, and returning to a trial with **Previous** resumes its provenance instead of starting over.
- **Accessibility**: Better button contrast, focus outlines that are no longer clipped, and other accessibility fixes throughout the participant interface.
